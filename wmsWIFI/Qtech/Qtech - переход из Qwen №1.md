НАЧАЛО ПРОТОКОЛА ДЛЯ НОВОЙ СЕССИИ

1. Архитектура и окружение

Хост: VM wmswifi, IP 192.168.12.154 (Hyper-V).
Путь к проекту: /opt/wimark/one.
Управление: Docker Compose.
Ключевые контейнеры:
one-nginx-proxy-ssl-1 — входная точка (проброс 80:80, 443:443)
one-wimark-web-client-1 — фронтенд (без прямого проброса порта, работает через nginx-proxy)
one-backend-golang-1 — бэкенд API
one-mongo-1 — MongoDB (порт 27017 внутри сети)
one-mosquitto-1 — MQTT-брокер, слушает 0.0.0.0:1883
one-configurer-golang-1 — конфигуратор устройств
Сеть Docker one_default — исправлена, DNS работает, все контейнеры на месте.
2. Решённые проблемы (НЕ ПОВТОРЯТЬ диагностику)

a) Недоступность веб-интерфейса (ERR_CONNECTION_REFUSED)

Причина: nginx-proxy-ssl не был подключён ни к одной Docker-сети.
Решение: docker compose up -d --force-recreate nginx-proxy-ssl из /opt/wimark/one — контейнер пересоздан и подключился к one_default. Веб-интерфейс доступен.
b) Предупреждение "Осталась лицензия на один портал"

Диагностика: ключ лицензии найден в MongoDB (test.wne_license_key, поле key — base64), лог license_log_daily подтверждал корректный учёт 8 CPE ранее.
Итог: бэкенд при запросах к /api/license стабильно отдаёт limit: 9, current: 9 без ошибок валидации. Лицензия активна и валидна, баннер пропал. Проблема не связана с лицензированием.
3. Текущая активная проблема

В интерфейсе Wimark ONE отображается 9 устройств QTECH QWP-82, все в статусе "офлайн", хотя физически пингуются (пример: Qtech-ef60 — 192.168.12.161).

Пароль root от веб-интерфейса LuCI устройств неизвестен, стандартные пароли не подходят, физический сброс не производился.

4. Проведённая диагностика по офлайн-статусу

Сетевая связность: порт 1883 (MQTT) снаружи доступен (nc -zv успешен), устройства пингуются.
Логи one-mosquitto-1: пусты — нет попыток подключения от IP устройств.
Логи one-configurer-golang-1: active_cpe_tunnels: null, CpeStates: {} — сервер не видит ни одного активного туннеля.
В БД (коллекции cpes/clients), объект config у всех точек доступа:
tunnels: {} — пусто
отсутствуют поля mqtt_host, broker_url, acs_url
beeline_config.nas_ip указывает на локальные IP самих точек доступа, а не на сервер управления
Глобальные настройки (system_configs, locations) не содержат параметров подключения к брокеру.
DHCP Option 43 — пользователь подтвердил, что не используется.
Применён шаблон QTECH QWP-82 через UI — статус устройств не изменился.
Коллекция config_rule ранее была пуста, требуется повторная проверка.
5. Текущая гипотеза

Точки доступа не знают адрес управляющего сервера. Поскольку DHCP Option 43 отключён, а в конфигурации устройств/глобальных настройках нет явного указания MQTT-брокера (192.168.12.154:1883), устройства работают автономно и не инициируют соединение. Применение шаблона через UI не сработало — либо сам шаблон не содержит параметров подключения, либо механизм применения шаблона неисправен.

6. Задачи для новой сессии (по приоритету)

Найти способ принудительно передать адрес MQTT-сервера (192.168.12.154:1883) устройствам Qtech без доступа к их веб-интерфейсу — через БД, API или альтернативный сервис автоконфигурации.
Проверить, почему применение шаблона QTECH QWP-82 не обновило конфигурацию устройств — проверить содержимое шаблона в БД (повторно config_rule) или логи применения шаблона.
Найти способ сбросить пароль на точках доступа удалённо (SNMP/TR-069, если поддерживается прошивкой), либо подтвердить необходимость физического сброса.
