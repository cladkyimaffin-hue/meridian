ПРОТОКОЛ ДЛЯ НОВОЙ СЕССИИ — Wimark ONE, диагностика IPsec/маршрутизации, сессия №3 (продолжение после сессий №1 и №2)

Скопируйте это целиком в начало нового чата вместе с файлами 000_ПромтИИ.txt и исходным протоколом сессии №2.

1. Архитектура (без изменений, см. исходный протокол)
Хост: VM wmswifi, IP 192.168.12.154 (Hyper-V)
Проект: /opt/wimark/one, управление Docker Compose
Ключевые контейнеры те же, включая one-strongswan-1 (network_mode: host, образ repo.wimark.local:5000/wne/strongswan:alpine-5.9.10)
Конфиги strongSwan: /opt/wimark/etc/strongswan/ (не стандартный /etc/)
2. Диагноз сессии №3 — НАЙДЕН И ПОДТВЕРЖДЁН
Корневая причина обрыва IPsec-туннелей (все точки кроме одной постоянно рвались каждые ~12 сек):

Файл /opt/wimark/etc/strongswan/ipsec.conf.tmpl был изменён сегодня, 20 июля, между 10:03 и 10:04 (обнаружено по timestamp двух бэкапов ipsec.conf.tmpl.backup_1784541773 и ipsec.conf.tmpl.backup_1784541864):

Было (рабочее состояние, backup_1784541773):

leftsubnet=10.9.0.0/16
rightsubnet=0.0.0.0/0
Стало (нерабочее состояние, backup_1784541864 = текущее на момент начала сессии №3):

leftsubnet=10.9.0.1/32
(rightsubnet удалён)

Механизм поломки: сужение leftsubnet до /32 убирало у ядра маршрут/XFRM-policy для возврата пакетов от клиентских виртуальных IP (пул 10.9.128.1–10.9.255.254/16, выдаётся через dnsmasq на lo, см. run.sh) обратно к серверу. Подтверждено командой на хосте:

ip route get 10.9.0.1 from 10.9.210.13
→ RTNETLINK answers: Network is unreachable
и пустым conntrack -L | grep 10.9.210.13 — пакеты от точек терялись до netfilter, на уровне маршрутизации ядра сразу после XFRM-декапсуляции. SYN-пакеты от точек долетали до eth0, но никогда не доходили до DNAT/mosquitto — отсюда wtm.up: Failed to setup tunnel to 192.168.12.154 на клиентах каждые ~12 сек (диагностировано через logread на точке .165, файл /usr/lib/lua/wtm/tunnels/ipsec.lua, функция ipsec_tcping на порт 1883 не проходила).

Важно: причина сегодняшнего изменения конфига (10:03-10:04) не установлена — неизвестно, кто и зачем менял leftsubnet. Это стоит выяснить отдельно (возможно, кто-то ещё работает с этим сервером, или это было частью другой, не задокументированной диагностики).

3. Предпринятые действия сессии №3 (в порядке выполнения)
Сделан бэкап текущего (нерабочего) состояния:
   /opt/wimark/etc/strongswan/ipsec.conf.tmpl.backup_before_revert_<timestamp>
Конфиг ipsec.conf.tmpl отредактирован обратно на рабочие значения:
   leftsubnet=10.9.0.0/16
   rightsubnet=0.0.0.0/0
Выполнен docker restart one-strongswan-1 — чтобы run.sh (entrypoint контейнера) пересоздал /etc/ipsec.conf из обновлённого шаблона (копирование происходит только при старте контейнера, см. содержимое run.sh ниже).
После рестарта пользователь потерял доступ по SSH/ping к хосту wmswifi (192.168.12.154) со своей рабочей машины.
4. Текущая НЕРЕШЁННАЯ проблема — потеря доступа к хосту
Симптомы:

❌ С рабочей машины пользователя: ping 192.168.12.154 не отвечает, SSH недоступен.
✅ С консоли Hyper-V (прямой доступ к хосту, не через сеть): всё выглядит нормально —
ip addr show eth0 — интерфейс UP, IP 192.168.12.154/24 на месте.
ip route show — маршрут по умолчанию default via 192.168.12.176 присутствует.
sshd запущен и слушает 0.0.0.0:22 (подтверждено через systemctl/journal, видно даже входящее Connection reset by 192.168.12.43).
sudo ufw status verbose — 22/tcp ALLOW IN Anywhere присутствует, политика deny incoming (default) не менялась подозрительно, явных блокирующих правил не видно.
Ping с хоста wmswifi до точки .165 (192.168.12.165) проходит нормально.
Гипотеза (не подтверждена, ~50%): временная нестабильность сетевого стека хоста из-за рестарта контейнера с network_mode: host — run.sh при каждом старте перевыполняет:

bash
sysctl -w net.ipv4.conf.all.rp_filter=2
echo 1 > /proc/sys/net/ipv4/ip_forward
for each in /proc/sys/net/ipv4/conf/*; do
    echo 0 > $each/accept_redirects
    echo 0 > $each/send_redirects
done
ip addr add 10.9.0.1/30 dev lo
Эти команды выполняются в net namespace хоста (не контейнера) из-за network_mode: host, и потенциально могли на краткое время сбросить ARP/связность на eth0. Не проверено: возможно, дело не во временном сбое, а в чём-то устойчивом.

Не проверено (следующие шаги для новой сессии):

Очистка ARP-кэша на рабочей машине пользователя (arp -d * в Windows) и повторный ping/SSH — предложено, результат неизвестен.
Проверить arp -a | grep 192.168.12.154 на хосте через консоль Hyper-V — не ушёл ли hostname/MAC в конфликт.
Проверить, не изменилось ли значение rp_filter на что-то, ломающее асимметричную маршрутизацию именно для входящих SSH-пакетов с рабочей машины (rp_filter=2 — loose mode, обычно безопасен, но стоит перепроверить net.ipv4.conf.eth0.rp_filter после рестарта).
Проверить dmesg/journalctl -xe на хосте на предмет сетевых ошибок именно в момент docker restart one-strongswan-1.
Попробовать SSH/ping с другой машины в той же сети (не только с рабочей машины пользователя) — чтобы понять, проблема глобальная (весь хост недоступен по сети) или локальная (что-то не так конкретно с маршрутом/ARP до машины пользователя).
Если ничего не поможет — рассмотреть полный docker restart или reboot хоста как крайнюю меру (через консоль Hyper-V, не по сети).
5. Если нужно ПОЛНОСТЬЮ откатить изменения сессии №3
Через консоль Hyper-V (или когда восстановится SSH):

bash
# Вернуть исходный (нерабочий по IPsec, но не трогавший сеть напрямую) конфиг:
cp /opt/wimark/etc/strongswan/ipsec.conf.tmpl.backup_1784541864 /opt/wimark/etc/strongswan/ipsec.conf.tmpl

# Перезапустить контейнер снова:

Важно: это НЕ гарантированно восстановит доступ по SSH, если причина потери доступа не связана с содержимым ipsec.conf.tmpl, а вызвана самим фактом рестарта host-network контейнера (см. гипотезу выше). Возможно, откат ничего не даст, и проблема с доступом либо временная и пройдёт сама, либо требует отдельного расследования.
