### 1. Краткое резюме (Executive Summary)
25 июня 2026 года была зафиксирована полная остановка сервиса Microsoft SQL Server, что привело к недоступности базы данных `LV_MERIDIAN` и остановке зависимых сервисов (Grafana, AI-middleware). Причиной стала истечение пробного периода (Evaluation) редакции Enterprise в сочетании с критическим повреждением системного исполняемого файла `sqlservr.exe` (размер стал равен 0 байт). В ходе восстановительных работ выполнена процедура Repair (восстановление) с использованием установочного образа, а также обновлена редакция до Standard Edition. На текущий момент сервер баз данных полностью функционирует, целостность данных сохранена.

### 2. Описание инцидента
Пользователями были зафиксированы ошибки подключения к базе данных. При попытке соединения через SSMS или клиентские приложения (Grafana, n8n) возвращалась ошибка:
> *Named Pipes Provider, error: 40 — Не удалось открыть подключение к SQL Server.*

Служба `MSSQLSERVER` находилась в состоянии `STOPPED` и не реагировала на попытки запуска.

### 3. Диагностика и выявление причин
В ходе диагностики были выполнены следующие шаги:
1.  **Проверка статуса службы:** Команда `sc query MSSQLSERVER` показала код выхода `17051`, что соответствует сообщению «Истек период оценки SQL Server».
2.  **Анализ журналов Windows:** В Event Viewer найдена запись (EventID 17051), подтверждающая истечение 180-дневного пробного периода редакции *Enterprise Evaluation Edition*.
3.  **Проверка версии:** Через реестр и командную строку подтверждено, что установлена версия SQL Server 2019 (RTM) редакции Enterprise Evaluation.
4.  **Выявление повреждения файлов:** При попытке запустить сервер в однопользовательском режиме (`-m`) возникла системная ошибка 193 («Не является приложением Win32»). Проверка файловой системы показала, что главный исполняемый файл `sqlservr.exe` имеет размер **0 байт**, что свидетельствует о его полном повреждении или удалении содержимого.

### 4. Выполненные работы по восстановлению
Так как стандартные методы обновления редакции (Edition Upgrade) были невозможны из-за неработающей службы и поврежденного бинарного файла, был применен следующий алгоритм:

1.  **Подготовка носителя:** Найден и смонтирован ISO-образ установщика Microsoft SQL Server 2019.
2.  **Запуск процедуры восстановления (Repair):** Через «Центр установки SQL Server» (Installation Center) выбрана опция «Обслуживание» -> «Восстановление».
3.  **Восстановление компонентов:** Указан путь к смонтированному ISO-диску. Система автоматически обнаружила поврежденные файлы (включая `sqlservr.exe`) и заменила их оригинальными копиями из дистрибутива.
4.  **Обновление редакции:** В процессе выполнения Repair было произведено изменение редакции с *Enterprise Evaluation* на *Standard Edition*, что сняло ограничение по времени использования.

### 5. Итоговый результат
После завершения работ выполнено тестирование:
*   Служба `MSSQLSERVER` успешно запущена и находится в состоянии `RUNNING`.
*   Проверка версии через `sqlcmd` подтвердила: *Microsoft SQL Server 2019 Standard Edition (64-bit)*.
*   База данных `LV_MERIDIAN` доступна, данные не пострадали.
*   Подключение из Grafana и других сервисов восстановлено.

### 6. Рекомендации по предотвращению повторения
1.  **Лицензирование:** Стандартная редакция также может иметь ограничения в зависимости от типа ключа. Рекомендуется проверить статус активации и при необходимости приобрести полноценную лицензию Standard Edition, чтобы избежать блокировки через 180 дней.
2.  **Мониторинг:** Настроить алертинг в системе мониторинга на статус службы MSSQLSERVER и наличие свободного места на диске (чтобы избежать повреждения файлов).
3.  **Резервное копирование:** Убедиться, что настроено регулярное резервное копирование базы `LV_MERIDIAN` на внешний носитель или отдельный сервер.

**Шаг 1. Проверка статуса лицензии и ключа продукта через реестр Windows**

Для проверки того, какой именно ключ используется и каков его статус (корпоративный или пробный), необходимо обратиться к системному реестру Windows Server. В SQL Server информация о ключе хранится в зашифрованном виде, но мы можем проверить идентификатор продукта (PID) и тип лицензии.

Выполните следующую команду в PowerShell или командной строке (cmd) от имени администратора на сервере **WMSDB (192.168.12.153)**:

```powershell
reg query "HKLM\SOFTWARE\Microsoft\Microsoft SQL Server\MSSQL15.MSSQLSERVER\Setup" /v PID
```

Также полезно проверить наличие ключа продукта в общем разделе установки:

```powershell
reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion" /v ProductId
```

**Что мы ищем:**
1.  Значение `PID` в первом запросе покажет идентификатор установленного экземпляра SQL Server. Если там указан стандартный набор символов без явных признаков корпоративного ключа (MAK/KMS), это может быть встроенный ключ установки.
2.  Для более детальной проверки типа активации можно использовать утилиту `slmgr.vbs` (если SQL использует системную активацию Windows) или специализированные скрипты Microsoft, но чаще всего в случае с переходом с Evaluation на Standard через Repair устанавливается «общий» ключ редакции, который требует ввода полноценного лицензионного ключа для снятия всех ограничений.

**Шаг 1. Объяснение природы «заглушки» (Generic Key) в SQL Server**

**Что это за цифры?**

**Откуда он взялся?**
Он появился автоматически во время процедуры **Repair (Восстановление)**, которую мы проводили 25 июня. Когда установщик SQL Server восстанавливает поврежденные файлы с ISO-образа, он прописывает в систему стандартный идентификатор для этой редакции (Standard Edition), чтобы программа могла запуститься. 

**Это как ключ?**
Нет, это не ключ активации в привычном понимании. 
*   **Настоящий ключ** (License Key) — это секретный код, который вы вводите при установке или обновлении, чтобы подтвердить право собственности. Он хранится в системе в зашифрованном виде и обычно скрыт от глаз даже администратора.
*   **Product ID (PID)** — это просто «паспорт» установленной программы. Цифры `90000` в этом паспорте говорят специалистам Microsoft: «Эта копия установлена с общего носителя, и уникальный ключ покупателя к ней пока не привязан».

**Где посмотреть настоящий ключ?**
Увидеть сам 25-значный ключ в открытом виде через реестр или стандартные команды Windows **невозможно** из соображений безопасности. Microsoft шифрует его сразу после ввода. 

Единственный способ узнать, есть ли у вас настоящий ключ — это:
1.  Найти бумажный договор или письмо от поставщика ПО (например, от «1С», «Softline» или другого вендора).
2.  Посмотреть в корпоративном портале лицензирования Microsoft (VLSC), если ваша компания там зарегистрирована.

**Протокол:**

*   Сам лицензионный ключ скрыт в недрах системы и не отображается в реестре.
