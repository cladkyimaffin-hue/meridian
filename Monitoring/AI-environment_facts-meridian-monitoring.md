## Эксплуатационные наблюдения

- Сеть `wmssql-analytics` была почти непригодна (2–6 КБ/с) через шлюз 192.168.12.176; через 192.168.12.1 около 760 КБ/с. После увеличения скорости роутера администратором работает нормально (VERIFIED, ADMIN). Доступ в Telegram с этой машины через оба шлюза недоступен (VERIFIED на дату проверки).
- DNS на `wmssql-analytics` (VERIFIED 2026-11-12): `/etc/resolv.conf` указывает на 1.1.1.1 и 8.8.8.8, запросы к 8.8.8.8 идут по таймауту, внутренний DNS 192.168.0.65 внешние имена не отдаёт. Из-за этого `docker pull` с Docker Hub бывает нестабилен (образ Caddy скачался со второй попытки), `ghcr.io` отвечает быстро.
- В `/etc/netplan` на `wmssql-analytics` лежат резервные копии `*.save` со старым адресом 192.168.12.154; рабочий адрес интерфейса — 192.168.12.202 (VERIFIED 2026-11-12). Адрес .154 принадлежит серверу `wmsWiFi` (ADMIN, 2026-11-12).
- `apt`/`dpkg` без терминала зависают на вопросах debconf: запускать с `< /dev/null` и `DEBIAN_FRONTEND=noninteractive`; после прерывания apt выполнить `dpkg --configure -a` (VERIFIED).
- Не использовать `pkill -f '<текст>'` внутри собственной команды: убивает свою же оболочку (VERIFIED).
- SSH-оболочка на Windows — `cmd`: нет `head` и `uname`; вывод в CP866 портится, для текста использовать `powershell -Command` с UTF-8. Строки с символом `|` в кавычках (регулярные выражения) через `powershell -Command` ломаются: использовать `-EncodedCommand` (VERIFIED, см. `COMMANDS.md`, блок 8).
- Нельзя «скрывать» секретные значения при выводе файла с помощью sed: маскировка не сработала, и хеш токена Vaultwarden попал в вывод (2026-11-12); токен перевыпущен (VERIFIED).
- После `docker kill` контейнер с политикой `restart: always` сам не поднялся (2026-11-16, `one-ntp-1`): останавливать контейнеры стека Qtech только после проверки последствий и запускать обратно сразу (VERIFIED).
