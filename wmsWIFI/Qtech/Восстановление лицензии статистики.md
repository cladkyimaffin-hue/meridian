**Шаг 5. Анализ монтирования томов MongoDB и проверка целостности данных**

Я проанализировал вывод `docker inspect`. Статус контейнера — `running`, что хорошо, но структура монтирования требует внимательной проверки, так как она нетипична для стандартного развертывания MongoDB.

**Фиксация фактов по монтированию:**
1.  **`/data/db` (Основная БД):** Смонтирована через bind mount из `/opt/mongodb/mongo` на хосте. Это правильное место хранения лицензий и конфигурации.
    *   *Риск:* Если после перезагрузки права доступа к папке `/opt/mongodb/mongo` изменились или она стала пустой/поврежденной, MongoDB могла запуститься, но не загрузить старые данные.
2.  **`/data/configdb`:** Использует анонимный volume Docker (`4a6f01...`).
    *   *Важно:* Анонимные volumes при пересоздании контейнера (если оно было) могут теряться, если не были явно сохранены. Однако здесь используется существующий volume, так что конфиги должны быть на месте.
3.  **`/data/scripts`:** Read-only bind mount из `/opt/wimark/one/db`. Это скрипты инициализации, они не влияют на хранение лицензий напрямую.

Возможно, при перезагрузке произошла ошибка файловой системы, или MongoDB при старте не смогла корректно прочитать файлы WAL/journal и откатила состояние базы до последнего консистентного снимка (который мог быть сделан до активации лицензии).

3.  Необходимо проверить, существуют ли файлы данных внутри этой папки и нет ли ошибок в логах MongoDB при старте.

## 1. Описание проблемы
**Симптом:** После перезагрузки сервера (VM Hyper-V) в веб-интерфейсе Wimak Platform (`https://192.168.12.154/aps`) появляется предупреждение: *«Осталось лицензия всего на одну аналитику (или меньше)...»*. Функции расширенной аналитики недоступны.

База данных `test` физически существует на диске, но логически не подключается движком из-за несоответствия файлов журналов и каталога `_mdb_catalog`. Бэкенд не может считать ключ лицензии из коллекции `wne_license_key`.

## 2. Архитектурный контекст
*   **Сервер:** `wmswifi` (Ubuntu 20.04, VM Hyper-V).
*   **БД:** MongoDB 5.0.23, контейнер `one-mongo-1`.
*   **Путь к данным:** Bind mount `/opt/mongodb/mongo` -> `/data/db` внутри контейнера.

### Шаг 3.1. Создание резервной копии (ОБЯЗАТЕЛЬНО)
Перед любыми действиями создайте архив текущих данных. Операция repair деструктивна для журналов транзакций.

```bash
docker stop one-mongo-1
tar -czf /opt/mongodb_backup_$(date +%Y%m%d_%H%M%S).tar.gz -C /opt mongodb/mongo
```

*Проверка целостности бэкапа:*
```bash
tar -tzf /opt/mongodb_backup_*.tar.gz | grep -E "WiredTiger|_mdb_catalog" | head -n 5
```

### Шаг 3.2. Выполнение ремонта базы данных
Запустите временный контейнер той же версии образа для безопасного восстановления метаданных. Оригинальный контейнер должен быть остановлен.

```bash
docker run --rm -v /opt/mongodb/mongo:/data/db mongo:5.0.23 mongod --dbpath /data/db --repair
```
*Ожидаемый результат:* Команда завершится с `exitCode: 0`. В логе должны присутствовать строки:
*   `"msg":"Repairing collection","attr":{"namespace":"test.wne_license_key"}`
*   `"msg":"Validation complete for collection. No corruption found"`
*   `"nrecords":1` (для коллекции лицензий)

*Критерий успеха:* Вывод содержит JSON-объект с полями `_id: 'wimark_license_key'` и `key: '...'`.

1.  Остановите контейнер: `docker stop one-mongo-1`
2.  Удалите поврежденные данные: `rm -rf /opt/mongodb/mongo/*`

**Шаг 1. Создание systemd-сервиса для корректной остановки MongoDB в Hyper-V**

Для предотвращения потери данных и повреждения метаданных WiredTiger при перезагрузке VM необходимо настроить службу, которая будет явно останавливать контейнер `one-mongo-1` до выключения хоста. Hyper-V передает сигнал ACPI Shutdown, но Docker может не успеть обработать его корректно без явной конфигурации.

**Действие:**
Создайте файл сервиса `/etc/systemd/system/wimark-mongodb-shutdown.service` со следующим содержимым:

```ini
[Unit]
Description=Graceful shutdown for Wimak MongoDB container
DefaultDependencies=no
Before=shutdown.target reboot.target halt.target
Conflicts=reboot.target halt.target shutdown.target

[Service]
Type=oneshot
ExecStart=/bin/true
ExecStop=/usr/bin/docker stop --time=30 one-mongo-1
TimeoutStopSec=45
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
```

Этот сервис гарантирует, что команда `docker stop` (которая отправляет SIGTERM и ждет 30 секунд) выполнится **до** начала аппаратного выключения системы. Таймаут увеличен с дефолтных 10 до 30 секунд, чтобы дать MongoDB время на финальный checkpoint.

**Протокол:**
1.  **Проблема:** При перезагрузке Hyper-V повреждаются метаданные WiredTiger из-за некорректной остановки контейнера.
2.  **Решение:** Systemd-сервис с приоритетом остановки перед shutdown.target.
3.  **Механизм:** Явный вызов `docker stop --time=30` вместо полагания на стандартный механизм остановки Docker daemon.
4.  **Безопасность:** Сервис типа `oneshot` с `RemainAfterExit=yes` не влияет на работу системы в штатном режиме, активируется только при остановке.

**Вопросы:**
Подтвердите создание файла и выполнение команд активации:
```bash
systemctl daemon-reload
systemctl enable wimark-mongodb-shutdown.service
```
После этого можно безопасно протестировать перезагрузку. Жду вашего «ОК».
