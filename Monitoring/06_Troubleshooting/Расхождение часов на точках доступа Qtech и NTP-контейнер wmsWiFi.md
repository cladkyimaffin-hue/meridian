# Расхождение часов на точках доступа Qtech и NTP-контейнер wmsWiFi

## Симптом

При подготовке дашборда «Wi-Fi: точки доступа» метрика `wifi_ap_clock_offset_seconds` показала, что часы восьми из девяти точек (`.158`, `.160`–`.166`) спешат относительно `wmsWiFi` на ≈954 с (≈16 минут), а часы точки `192.168.12.159` отстают на 46,85 суток (−4 048 042 с). Восемь точек синхронны между собой. На радиосвязь это не влияет, но в журналах точек даты неверны. Плитка «Расхождение часов» стала красной (порог красного — отклонение больше 1 часа).

## Диагностика (VERIFIED, 2026-11-16, чтение)

- Хост `wmsWiFi` синхронизируется службой `systemd-timesyncd` с `ntp.ubuntu.com` (185.125.190.57), слой 2, «System clock synchronized: yes», время UTC. Его часы верные: три российских сервера (46.188.16.150, 185.209.85.222, 91.207.136.55) отвечают с разницей 0 с.
- Адрес `10.9.0.1` — адрес самого `wmsWiFi` (`lo 10.9.0.1/30`). Восемь точек получают время от него, то есть от контейнера Qtech `one-ntp-1` (порт UDP 123, политика `restart: always`).
- Сам `one-ntp-1` не был синхронизирован: `chronyd` запущен с ключом `-x` (не управляет часами), источников 0 (в журнале с 3 августа «no selectable sources»), в файле дрейфа записана частота −105,97 ppm. За 104 дня это даёт ≈953 с, что совпадает с наблюдаемой ошибкой (INFERRED по совпадению цифр). Контейнер отдавал время на ≈16 минут вперёд, ошибка росла примерно на 9 с в сутки. Точки подстроились под него, поэтому их сдвиг относительно своего источника был малым.
- Точка `.159` брала время с `10.3.30.26`, который не отвечает, поэтому её часы остановились на 30 сентября (47 суток назад).
- Часовой пояс на всех точках `Europe/Moscow`, `ntpd` запущен везде.

## Решение (выполнено 2026-11-16 после «да» администратора, время около 14:15 МСК)

1. **Контейнер `one-ntp-1`** [W]: внутри удалён файл дрейфа `/var/lib/chrony/chrony.drift` (значение −105,968902 ppm сохранено в копии `~/chrony.drift.bak-20261116` на хосте), контейнер перезапущен. Перезапуск сделан командой `docker kill`, после неё контейнер не поднялся, NTP-сервер стоял несколько минут, пока его не запустили вручную (`docker start`, 11:13:38 UTC). Это ошибка исполнителя (не проверено заранее поведение `restart: always` при ручной остановке); точки связи не потеряли.
2. **Точка `.159`** [W]: источник времени заменён на `10.9.0.1` (`uci set system.ntp.server='10.9.0.1'` и `uci commit system`, как у остальных).
3. **Все девять точек** [W]: время выставлено командой `date -u -s` по часам `wmsWiFi`, перезапущена служба `sysntpd`.
4. **Проверка NTP в опроснике** [W]: службу `wifi-ap-exporter` обновили скриптом `update.sh` (запустил администратор с `sudo`): копия `wifi-ap-exporter.py.bak-20261116`, новый файл, перезапуск; добавлена проба сервера `10.9.0.1` — метрики `wifi_ntp_server_up`, `wifi_ntp_server_offset_seconds`, `wifi_ntp_server_stratum`.

## Проверка результата

- [x] Контейнер `one-ntp-1` теперь синхронизирован с внешним сервером `46.188.16.150`, слой 3, ошибка 0,002 с.
- [x] Сервер времени отдаёт верное время на 127.0.0.1, 192.168.12.154 и 10.9.0.1 (разница 0 с).
- [x] На всех девяти точках `ntp.server=10.9.0.1`; сдвиг часов −1…−2 с через минуту после выставления; максимальный сдвиг 2 с; все девять точек `up`.
- [x] После `update.sh`: служба `active`, `wifi_ntp_server_up` 1, сдвиг −0,003 с, слой 3.
- [ ] Не проверено: продержится ли синхронизация контейнера (раньше он терял источники через 7 секунд после неудачного перевода часов, теперь этого не случилось) — посмотреть по дашборду через несколько дней.
- [ ] Не подтверждено: добавлены ли панели NTP в дашборд «Wi-Fi: точки доступа» (их добавление было начато в конце чата, результат в материалах отсутствует; UNKNOWN).

## Откат

- Файл дрейфа [W]: вернуть файл со значением −105,968902 ppm из `~/chrony.drift.bak-20261116` внутрь контейнера и перезапустить (`docker restart one-ntp-1`). Возвращать нет смысла: это возобновит ошибку.
- Источник времени точки `.159` [W]: `uci set system.ntp.server='10.3.30.26'`, `uci commit system`, перезапустить `sysntpd`; делать не нужно, адрес не отвечает.
- Опросник точек [W]: `sudo cp /opt/wifi-ap-exporter/wifi-ap-exporter.py.bak-20261116 /opt/wifi-ap-exporter/wifi-ap-exporter.py && sudo systemctl restart wifi-ap-exporter`.
- Время на точках откатить нельзя (скачок необратим по смыслу): ориентироваться на верное время.

## Что остаётся нерешённым

- Прочность исправления контейнера `one-ntp-1` (см. «Don't repeat»); прочный вариант — отдельное решение администратора (источники времени у `chronyd` или правка `docker-compose.yml` Qtech в `/opt/wimark/one`).
- Контроллер Qtech может при отправке конфигурации снова записать на точки другой источник времени.
- Две точки (`.161` и `.163`) перезагрузились около семи часов до обращения (остальные работали 84–90 суток); причина неизвестна (UNKNOWN: питание, контроллер Qtech или другое).
