1. Разверните ядро в Docker Compose

Prometheus и Grafana с зафиксированными версиями образов (не latest).

Для MSSQL заведите отдельный логин с минимальными правами (VIEW SERVER STATE, VIEW ANY DEFINITION), не sa.

Сам wmsDB-TEST (node_exporter или windows_exporter, смотря какая там ОС).
Один MSSQL.
Сам Prometheus (он мониторит сам себя).

Когда эти три работают и дашборды показывают нормальные данные, добавляйте Hyper-V, Synology и SNMP. Так проще понять, где что ломается.

4. Уточнения к тексту выше

В windows_exporter уже есть встроенный коллектор mssql и коллектор hyperv. Для базовых метрик MSSQL на Windows отдельный экспортер часто не нужен.

Пока Zabbix отвечает за up/down и уведомления, не дублируйте алерты. Сначала наберите историю и дашборды, поймите нормальные значения, а потом решайте, что переносить в Alertmanager. Это избавит от потока ложных срабатываний.

Вариант 1. Ограниченный sudo (рекомендую)

Разрешаем только то, что нужно для установки и удаления: apt, dpkg, systemctl. Выполните на сервере:

bash
sudo visudo -f /etc/sudoers.d/claude-ops
и вставьте строку:

user ALL=(root) NOPASSWD: /usr/bin/apt-get, /usr/bin/apt, /usr/bin/dpkg, /usr/bin/systemctl
Затем создайте рабочую папку, чтобы файлы конфигов не требовали root:

bash
sudo mkdir -p /opt/monitoring && sudo chown user:user /opt/monitoring
После установки Docker (его CLI) работа с контейнерами пойдёт через группу docker, sudo для неё не нужен.

Вариант 2. Временный полный доступ

user ALL=(ALL) NOPASSWD: ALL
Удобнее, но шире, чем нужно. Если выбираете его, удалите файл сразу после работы.

Вариант 3. Без доступа

Я выдаю команды, вы выполняете их сами и присылаете вывод, а я проверяю результат. Медленнее, зато вы контролируете каждый шаг.

Что важно понимать

Доступ к apt и dpkg без пароля по сути равен root. Скрипты пакетов выполняются от root, так что это не настоящее ограничение, а скорее защита от случайных ошибок. Та же логика у группы docker, в которой user уже состоит.
Удалить доступ можно одной командой: sudo rm /etc/sudoers.d/claude-ops. Я бы выдал его только на время работ.
Все sudo-вызовы пишутся в /var/log/auth.log, так что действия можно потом проверить.
Правки в /etc/sudoers.d делайте только через visudo, он проверяет синтаксис. Ошибка в sudoers может отнять sudo совсем.
