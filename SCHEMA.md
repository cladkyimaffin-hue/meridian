# 📐 SCHEMA.md — канонический формат метаданных документа (общее ядро)

Этот файл — единственный источник правды о том, какие поля фронтматтера обязательны, а какие опциональны, для **всех доменов** репозитория `meridian`. Структура перенесена из репозитория `korona` (версия схемы 1.1) без изменения ядра.

Доменные файлы `<домен>/00_Meta/SCHEMA.md` содержат только то, что зависит от домена. Если доменный файл противоречит этому файлу — приоритет у этого файла, а расхождение записывается в `<домен>/00_Meta/CONFLICTS.md`.

Конвейер (ИИ или скрипт), обрабатывающий любой документ, обязан сверяться с этим файлом, а не с соседними документами: они могут быть написаны по старой версии схемы (см. раздел 3).

---

## 1. Обязательное ядро (15 полей)

Присутствует в **каждом** документе без исключений. Скрипта автоматической проверки в репозитории пока нет, проверка ручная (минимальный аудит — в `AI-NEW-CHAT-CONTEXT.md`, раздел 5).

```yaml
document_id: ""        # уникален в пределах registry.csv своего домена, формат см. ниже
title: ""               # человекочитаемое название, совпадает с H1 в теле файла
document_type: ""       # runbook | troubleshooting | reference | setup | meta
status: ""               # draft | in_progress | completed | archived
priority: ""             # critical | high | medium | low | info
date_created: 2026-01-01
date_modified: 2026-01-01
next_review: 2026-01-01
author: ""
category: ""              # имя целевой папки домена; список — в AI-README.md домена
tags: []                  # значения только из <домен>/00_Meta/TAGS.md
ai_summary: ""            # 1-2 предложения, по которым ИИ находит документ без чтения всего тела
dont_repeat: []            # запреты и грабли из этого документа; если нет — []
related_files: []          # document_id связанных документов (не имена файлов)
schema_version: "1.1"      # версия ЭТОЙ схемы, под которую написан документ — см. раздел 3
```

### Формат `document_id`

`<ОБЛАСТЬ>-<ТЕМА>-<ГГГГ>-<NNN>`, например `MONITORING-WINDOWS-EXPORTER-2026-001`. Уникальность проверяется по `registry.csv` домена перед присвоением, ID не изобретается на глаз.

## 2. Опциональный расширенный блок

Добавляется **только если документ реально об этом**. Лучше отсутствие поля, чем поле со значением `""`.

```yaml
environment: ""       # production | staging | test
target_system: ""
hostname: ""
node: ""               # имя сервера или устройства; значения — в файле фактов домена
cluster: ""             # если применимо
vm_id: ""
keywords: []             # альтернативные формулировки для полнотекстового поиска
aliases: []               # другие названия того же инцидента или документа
confidentiality: ""       # public | internal (по умолчанию internal)
superseded_by: ""         # document_id заменившего документа; указывается вместе со status: archived
last_verified: 2026-01-01 # дата последней сверки фактов с живой системой; не равна date_modified
```

Поле существует в схеме, только если хотя бы один реальный документ заполнил его осмысленным значением.

---

## 3. Принцип эволюции схемы

Схема меняется аддитивно и по ситуации, без ретроактивного переписывания того, что не затронуто.

1. Документ под `schema_version: "1.0"` остаётся под ней, пока его не редактируют. Массовая миграция автоматически не выполняется.
2. Если документ редактируется по факту реального изменения, он поднимается до текущей версии схемы, и только он.
3. Каждое изменение схемы фиксируется в разделе 4 с датой и причиной.
4. Breaking change (переименование поля, смена формата) допускается только с записью в `<домен>/00_Meta/CONFLICTS.md` и подтверждением администратора. Добавление опциональных полей breaking change не является.
