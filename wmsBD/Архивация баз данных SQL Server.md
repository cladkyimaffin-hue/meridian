**Шаг 1.1 — Определение текущего размера баз данных в MSSQL**

Для расчёта необходимого места на Synology NAS сначала нужно узнать фактический размер всех пользовательских баз данных на MSSQL 2019.

Выполни следующий SQL-запрос в SQL Server Management Studio (SSMS) или через `sqlcmd`:

```sql
SELECT 
    DB_NAME(database_id) AS DatabaseName,
    CAST(SUM(CASE WHEN type = 0 THEN size END) * 8.0 / 1024 AS DECIMAL(18,2)) AS DataSizeMB,
    CAST(SUM(CASE WHEN type = 1 THEN size END) * 8.0 / 1024 AS DECIMAL(18,2)) AS LogSizeMB,
    CAST(SUM(size) * 8.0 / 1024 AS DECIMAL(18,2)) AS TotalSizeMB
FROM sys.master_files
WHERE database_id > 4  -- исключаем системные базы
GROUP BY database_id
ORDER BY TotalSizeMB DESC;
```

Этот запрос покажет:
- Имя каждой пользовательской базы
- Размер файлов данных (`.mdf` / `.ndf`) в МБ
- Размер файлов журнала (`.ldf`) в МБ
- Общий размер базы в МБ

> **Примечание:** при резервном копировании (`BACKUP DATABASE`) размер бэкапа обычно меньше размера файлов данных за счёт сжатия и отсутствия неиспользуемого пространства. Но для расчёта места на NAS мы будем отталкиваться именно от фактического размера, чтобы заложить запас.

**Шаг 2.1 — Фиксация способа подключения NAS и проверка видимости пути для службы SQL Server**

Зафиксировано: на Synology создана папка `LV_MERIDIAN`; на сервере MSSQL подключён сетевой диск `Z:\LV_MERIDIAN`.

**Критичный факт, который нужно учесть сейчас (проверяемо, Microsoft Learn):**
1. Команда `BACKUP DATABASE` выполняется процессом SQL Server Database Engine, который работает как служба Windows в изолированной сессии 0 (Session 0 Isolation). Буквенные диски (Z:) отображаются только в пользовательских сеансах входа, в которых они созданы; службе они **не видны**. Поэтому путь `Z:\LV_MERIDIAN` в `BACKUP DATABASE` у службы не найдётся (ошибка открытия устройства резервного копирования, OS error 3 — путь не найден).
2. Согласно документации Microsoft по резервному копированию SQL Server, для бэкапа на сетевой ресурс используется **UNC-путь** (`\\имя_ресурса\папка\...`), а учётной записи, под которой работает служба Database Engine, должны быть выданы права записи на этот ресурс.

**Действие этого шага — собрать два факта:**

1. Точный UNC-путь, соответствующий диску Z:. На сервере MSSQL в командной строке:
```
net use
```
(выведет таблицу: буква диска → UNC-путь ресурса).

2. Учётная запись службы SQL Server. В SSMS выполнить:
```sql
SELECT servicename, service_account
FROM sys.dm_server_services;
```
(DMV документирована: Microsoft Learn, «sys.dm_server_services (Transact-SQL)»).

**Шаг 2.7 — Рассмотрение альтернативных вариантов бэкапа (включая средства Synology)**

Отвечаю по факту: у Synology есть собственный продукт для защиты серверов, плюс есть два обходных технических решения, которые вообще убирают проблему аутентификации SMB. Разбираю все три варианта.

**Вариант 1 — Synology Active Backup for Business (штатное средство NAS)**
- Как работает: на сервер WMSDB ставится агент Synology; при активации агента в консоли задаются адрес NAS и учётные данные DSM — то есть к NAS ходит **агент со своими явно заданными учётными данными**, а не служба SQL Server. Проблема 1326 при этом не возникает вовсе.
- Что даёт: централизованное управление с NAS, политики хранения/версий, дедупликация — всё штатно (документация Synology, help.synology.com, раздел Active Backup for Business).
- **Ограничение (честно помечаю как непроверенное):** в моих достоверных сведениях Active Backup for Business — это файловое/образное резервное копирование серверов и ВМ (с VSS для согласованности), а наличие нативного модуля под MS SQL (бэкап на уровне баз с восстановлением как из .bak) я подтвердить не могу. Перед выбором этого варианта нужно свериться с актуальной спецификацией ABB для вашей версии DSM. Восстановление в файловом режиме = возврат файлов MDF/LDF или всего сервера, а не restore базы.

**Вариант 2 — iSCSI-ЛУН от Synology как «локальный диск»**
- Как работает: NAS (SAN Manager в DSM 7 / iSCSI Manager в DSM 6) отдаёт LUN; встроенный в Windows «iSCSI-инициатор» подключает его как локальный диск (например, E:). `BACKUP DATABASE` пишет на него как на обычный локальный диск — **аутентификации Windows/SMB нет вообще** (на блочном уровне — CHAP или без аутентификации), значит 1326 невозможен, учётку службы не трогаем.
- Источники: документация Synology по iSCSI/SAN Manager; документация Microsoft по Microsoft iSCSI Initiator.
- Минус: очистку старых .bak (7 дней) по-прежнему нужно организовывать скриптом/заданием — NAS за это здесь не отвечает.

**Вариант 3 — Локальный бэкап + копирование на NAS отдельным процессом**
- Как работает: `BACKUP DATABASE` пишет на локальный диск WMSDB (у службы всегда есть локальные права); затем отдельный процесс, запущенный под учёткой с действующими учётными данными NAS (`sqlbackup` или «Administrator»), копирует .bak на `\\wmsbackup\LV_MERIDIAN` и удаляет файлы старше 7 дней. Исполнитель: Планировщик заданий Windows (задача от нужной учётки) или задание SQL Agent (шаг CmdExec через прокси-учётную запись — документировано Microsoft, msdb proxies).
- Плюс: не меняем учётку службы, на NAS лежат нативные .bak. Минус: два механизма вместо одного (бэкап + копирование/очистка).

**Сводка:**

| Критерий | Смена учётки службы (уже одобрено ранее) | Active Backup for Business | iSCSI | Локально + копирование |
|---|---|---|---|---|
| Нативный .bak на NAS | да | нет (файловый уровень) | да | да |
| Не трогать учётку службы | нет | да | да | да |
| Хранение 7 дней штатно | нужен скрипт очистки | да, в консоли NAS | нужен скрипт | скрипт в задаче |
| Статус проверки | проверено нами | требует сверки со спецификацией ABB вашей DSM | стандартные механизмы | стандартные механизмы |

Моё предложение по приоритету (по вашей инициативе о приоритизации): если приемлемо файловое/образное восстановление — проверить ABB (вариант 1); если нужен нативный .bak без смены учётки службы — iSCSI (вариант 2); вариант 3 — как самый консервативный запасной.

**Действие — создать процедуру восстановления в master** (синтаксис и команды — по документации Microsoft Learn: CREATE OR ALTER PROCEDURE, RESTORE HEADERONLY, RESTORE VERIFYONLY, RESTORE WITH REPLACE, ALTER DATABASE SET SINGLE_USER/MULTI_USER):

```sql
USE master;
GO

CREATE OR ALTER PROCEDURE dbo.Restore_LV_MERIDIAN
    @FileName   NVARCHAR(260),   -- имя файла или полный путь к .bak
    @VerifyOnly BIT = 0          -- 1 = только проверка файла, без восстановления
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @path NVARCHAR(260) = @FileName;
    IF @path NOT LIKE N'\\%'
        SET @path = N'\\wmsbackup\LV_MERIDIAN\' + @FileName;

    -- Режим проверки: целостность копии без воздействия на базу
    IF @VerifyOnly = 1
    BEGIN
        RESTORE VERIFYONLY FROM DISK = @path;
        PRINT N'Проверка завершена: ' + @path;
        RETURN;
    END;

    -- Сведения о выбранной копии (заголовок бэкапа)
    RESTORE HEADERONLY FROM DISK = @path;

    -- Эксклюзивный режим и восстановление поверх текущей базы
    ALTER DATABASE [LV_MERIDIAN] SET SINGLE_USER WITH ROLLBACK IMMEDIATE;

    RESTORE DATABASE [LV_MERIDIAN]
    FROM DISK = @path
    WITH REPLACE, STATS = 10;

    ALTER DATABASE [LV_MERIDIAN] SET MULTI_USER;
END;
GO
```

**Заложенная логика безопасности (прозрачно):**
- Если файл не найден или не является корректным бэкапом, ошибка возникнет на стадии VERIFYONLY/HEADERONLY — процедура прервётся **до** перевода базы в SINGLE_USER, база не пострадает.
- Если ошибётся сам RESTORE, база может остаться в SINGLE_USER — возврат: `ALTER DATABASE [LV_MERIDIAN] SET MULTI_USER;`.
- Процедура размещена в master намеренно: master не восстанавливается вместе с пользовательскими БД и процедура доступна всегда, включая момент, когда LV_MERIDIAN недоступна.

**Шаг 5.3 — Автономный скрипт восстановления LV_MERIDIAN с подстановкой файла бэкапа**

Скрипт ниже эквивалентен процедуре `master.dbo.Restore_LV_MERIDIAN`, но выполнен как единый самодостаточный блок с полем подстановки и гарантированной обработкой ошибок через TRY/CATCH (документация Microsoft Learn: BEGIN TRY...END TRY / CATCH, ERROR_MESSAGE(); RESTORE VERIFYONLY; ALTER DATABASE SET SINGLE_USER/MULTI_USER; колонки sys.databases).

```sql
USE master;
GO

-- >>> ПОДСТАВЬТЕ ИМЯ ФАЙЛА БЭКАПА (или полный путь) <<<
DECLARE @FileName NVARCHAR(260) = N'LV_MERIDIAN_15082026_210000.bak';
-- ------------------------------------------------------

DECLARE @path NVARCHAR(260) = @FileName;
IF @path NOT LIKE N'\\%'
    SET @path = N'\\wmsbackup\LV_MERIDIAN\' + @FileName;   -- путь по умолчанию

BEGIN TRY
    -- 1) Проверка файла: при ошибке уходим в CATCH, база НЕ затрагивается
    RESTORE VERIFYONLY FROM DISK = @path;
    PRINT N'Файл корректен: ' + @path;

    -- 2) Эксклюзивный режим (все подключения к LV_MERIDIAN будут завершены)
    ALTER DATABASE [LV_MERIDIAN] SET SINGLE_USER WITH ROLLBACK IMMEDIATE;

    -- 3) Восстановление поверх текущей базы
    RESTORE DATABASE [LV_MERIDIAN]
    FROM DISK = @path
    WITH REPLACE, STATS = 10;

    -- 4) Возврат в рабочий режим
    ALTER DATABASE [LV_MERIDIAN] SET MULTI_USER;
    PRINT N'Восстановление завершено из файла: ' + @path;
END TRY
BEGIN CATCH
    PRINT N'ОШИБКА: ' + ERROR_MESSAGE();
    -- если база осталась в SINGLE_USER и онлайн — возвращаем в MULTI_USER
    IF EXISTS (SELECT 1 FROM sys.databases
               WHERE name = N'LV_MERIDIAN'
                 AND state_desc = N'ONLINE'
                 AND user_access_desc = N'SINGLE_USER')
        ALTER DATABASE [LV_MERIDIAN] SET MULTI_USER;
END CATCH
GO
```

**Как пользоваться:**
1. Открыть папку `\\wmsbackup\LV_MERIDIAN` в проводнике, выбрать файл по имени (`LV_MERIDIAN_ДДММГГГГ_ЧЧММСС.bak` = дата и время создания копии).
2. Вставить имя в `@FileName` (кавычки и префикс `N` сохранить).
3. Выполнить скрипт целиком в SSMS на WMSDB под `sa`.

**Предупреждения (следствия документированных опций):**
- `WITH ROLLBACK IMMEDIATE` принудительно завершит все активные подключения к LV_MERIDIAN на время восстановления.
- `WITH REPLACE` перезапишет текущую базу; изменения позже момента выбранной копии будут потеряны.

**Шаг 5.4 — Возможен ли диалог выбора файла в скрипте: разбор вариантов**

**Прямой ответ:** чистый T-SQL открыть диалоговое окно **не может** — T-SQL выполняется на сервере (Database Engine) и не имеет никаких GUI-API. Окно выбора файла — это всегда клиентская часть. Отсюда три рабочих варианта, от честного минимума к полноценному окну:

**Вариант 1 — Штатный диалог SSMS (скрипт вообще не нужен).**
Правой кнопкой по базе → **Задачи** → **Восстановить** → **База данных…** → источник «Устройство» → «…» → «Добавить» — откроется окно «Расположение файлов резервных копий», где можно вписать/обзорать `\\wmsbackup\LV_MERIDIAN` и выбрать .bak. Это и есть диалог выбора файла, документирован Microsoft Learn («Restore a Database Using the Restore Database Dialog Box»). Минус: это ручное восстановление средствами SSMS, а не наш скрипт/процедура.

**Вариант 2 — PowerShell-скрипт с настоящим окном выбора (рекомендую, если нужно именно окно).**
Запускается в вашей RDP-сессии (GUI есть): скрипт открывает системное окно выбора файла (.NET `OpenFileDialog`, документировано Microsoft) с начальной папкой `\\wmsbackup\LV_MERIDIAN` и фильтром `*.bak`, а после выбора выполняет восстановление на сервере через `Invoke-Sqlcmd` (документировано, модуль SqlServer) — вызовом нашей процедуры `master.dbo.Restore_LV_MERIDIAN` или автономного скрипта шага 5.3. Получаем именно «скрипт + диалог».

**Вариант 3 — «Псевдодиалог» внутри SSMS: список файлов с номерами.**
T-SQL выводит пронумерованный список .bak из папки NAS, админ подставляет номер/имя в переменную — восстановление идёт из выбранного. Для листинга папки из T-SQL нужен `xp_cmdshell 'dir …'` (документирован Microsoft Learn, но по умолчанию отключён; включение — осознанное действие с последствиями для безопасности) либо `xp_dirtree` (работает, но **не документирован** Microsoft — помечаю честно). Окна нет, но выбор из списка на экране.

**Шаг 5.5 — Вариант 1 подробно: восстановление LV_MERIDIAN через штатный диалог SSMS с выбором файла**

Это встроенный диалог восстановления SSMS (документировано Microsoft Learn, «Restore a Database Using the Restore Database Dialog Box»); русские подписи могут незначительно отличаться в зависимости от языкового пакета.

**Пошагово:**
1. В обозревателе объектов правой кнопкой по базе **LV_MERIDIAN** → **Задачи** → **Восстановить** → **База данных…**.
2. Откроется окно «Восстановление базы данных», страница **Общие**.
3. Секция **Источник**: переключатель **Устройство** → кнопка **«…»** справа.
4. Окно «Выбор устройства резервного копирования» → **Добавить**.
5. Окно «Расположение файлов резервных копий» — это и есть диалог выбора файла:
   - обзор работает **на стороне сервера** под учётной записью Engine (`.\sqlbackup`), у которой есть доступ к NAS — папка `\\wmsbackup\LV_MERIDIAN` доступна;
   - если сетевой папки не видно в дереве — просто впишите полный путь в поле «Имя файла:»: `\\wmsbackup\LV_MERIDIAN\LV_MERIDIAN_15082026_210000.bak` → **ОК**.
6. В списке устройств появится выбранный .bak → **ОК**. На странице «Общие» в таблице «Наборы резервных копий для восстановления» появится строка с галкой — убедитесь, что галка стоит; в секции **Назначение** база = `LV_MERIDIAN`.

   - **Перезаписать существующую базу данных (WITH REPLACE)** — без неё восстановление поверх существующей базы не выполнится;

8. **ОК** — запуск восстановления; внизу прогресс, по завершении — сообщение об успехе.

**Дополнительные факты и возможности:**
- Кнопка **«Сценарий»** в верхней панели диалога выводит эквивалентный T-SQL (RESTORE … WITH REPLACE и т.д.) в новое окно запроса — можно сохранить как готовый скрипт именно с выбранным файлом.

**Предупреждения (те же, что у боевого восстановления):** `WITH REPLACE` перезаписывает текущую базу — изменения позже момента выбранной копии теряются; подключения к LV_MERIDIAN будут завершены.
