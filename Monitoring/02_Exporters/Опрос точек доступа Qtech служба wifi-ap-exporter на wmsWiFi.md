# Опрос точек доступа Qtech: служба wifi-ap-exporter на wmsWiFi

## Что настраивается и зачем

Девять точек доступа Qtech на складе нельзя мониторить обычным exporter: места на флеш-памяти точки мало. Поэтому на сервере `wmsWiFi` (Linux-ВМ 192.168.12.154 со стеком Qtech в Docker) работает служба `wifi-ap-exporter`: она раз в минуту заходит на каждую точку по SSH, читает состояние и отдаёт метрики для Prometheus на `wmssql-analytics` (192.168.12.202). Метрики показывает дашборд «Wi-Fi: точки доступа» (`MONITORING-DASHBOARDS-APP-HOST-WIFI-2026-001`). Сам сервер `wmsWiFi` подключен отдельно через `node-exporter` (порт 9100).

## Решения администратора (2026-11-15 и 2026-11-16)

| Вопрос | Решение |
|---|---|
| Как мониторить точки | опрос по SSH с `wmsWiFi`; агенты на точки не ставить (администратор сообщил, что на точки можно зайти по SSH, нужен вход по ключу) |
| Ключ | отдельный ключ без пароля, чтобы доступ работал без участия человека; открытую часть на точки устанавливает администратор (пароль точек вводит сам) |
| Сколько точек | девять, десятой нет |
| Служба | `wifi-ap-exporter` на `wmsWiFi`; «да» после показа кода и списка команд на точках |
| Установка | скрипт `install.sh` запускает администратор с `sudo`; правило `ufw` тоже он |
| Prometheus | подключить `wmsWiFi` (порт 9100) и опрос точек (порт 9877), «да» |

## Предварительные условия (VERIFIED, 2026-11-15 и 2026-11-16, только чтение)

- `wmsWiFi`: Ubuntu, ядро Linux 6.8.0-136-generic; вход администратора по SSH; в Docker стек Qtech. `ufw` включён.
- Точки доступа (192.168.12.158–166): прошивка Wimark v1.15.2-e (платформа ramips/mt7621), работают 83–89 суток, нагрузка 0–0,17, свободно около 126–128 МБ из 250 МБ ОЗУ, overlay 2,9 МБ (занято 14 %); в Wi-Fi одно имя сети на всех, каналы 2,4 ГГц: 1, 6, 11, 5 ГГц: 40, 44, 48, 52, 56, 132, 136. У `.159`–`.163` все радио 2,4 ГГц на канале 1 (INFERRED: возможное пересечение каналов, при малой нагрузке не проблема).
- Вход по SSH на точку: штатная учётная запись администратора точки, пароль знает администратор; на точке BusyBox и `dropbear`, ключи читаются из `/etc/dropbear/authorized_keys` (VERIFIED по тестовому входу).
- Порт 9877 на `wmsWiFi` свободен.

## Шаги

Все шаги [W], выполнены 2026-11-15 и 2026-11-16. Общие команды — в этом документе, `COMMANDS.md` не дополнялся.

1. **Ключ на `wmsWiFi`:** создан `~/.ssh/id_ed25519_ap` (закрытая часть, права 600, без пароля) и `id_ed25519_ap.pub`; существующий `authorized_keys` не менялся. Отпечаток открытой части: `SHA256:zZBSQCRjMS9T8+RiRY0QhqG1GPY0sB3UYvLJv5nQfLo`; комментарий ключа `monitoring-ap@wmswifi`.
2. **Ключ на точках** (делает администратор): на первой точке (`.158`) строку открытой части вставили в `/etc/dropbear/authorized_keys` и выставили права 600; затем на остальных восьми цикл с `wmsWiFi`:

   ```bash
   for i in $(seq 159 166); do echo "== 192.168.12.$i"; cat ~/.ssh/id_ed25519_ap.pub | ssh -o StrictHostKeyChecking=accept-new root@192.168.12.$i 'mkdir -p /etc/dropbear && cat >> /etc/dropbear/authorized_keys && chmod 600 /etc/dropbear/authorized_keys'; done
   ```

   Команда добавляет строку в конец файла и запоминает отпечатки точек в `known_hosts` на `wmsWiFi`; при повторном запуске строка продублируется (безвредно). Здесь `root` — стандартная учётная запись прошивки точки.
3. **Служба:** скрипт `install.sh` (подготовлен Claude, запущен администратором с `sudo`): проверяет, что установки ещё нет и ключ читается; создаёт `/opt/wifi-ap-exporter/wifi-ap-exporter.py` (владелец root) и `/etc/systemd/system/wifi-ap-exporter.service` (запуск от непривилегированной учётной записи администратора, у которой лежит ключ; `Restart=on-failure`, перезапуск через 10 с, нет повышения прав, домашний каталог только для чтения, `ProtectSystem=strict`; запуск после `network-online.target`); включает автозапуск; правила `ufw` скрипт не меняет.
4. **Порт:** администратор добавил правило `ufw` [W]:

   ```bash
   sudo ufw allow from 192.168.12.202 to any port 9877 proto tcp comment 'Prometheus wifi-ap-exporter'
   ```
5. **Prometheus на `wmssql-analytics`** [W]: копия `prometheus.yml.bak-20261116`; в `prometheus.yml` в задаче `node_linux` добавлена цель `192.168.12.154:9100` (`host: wmsWiFi`) и новая задача `wifi_ap` с файлом целей `targets/wifi.yml` (цель `192.168.12.154:9877`, метки `host: wmsWiFi`, `role: wifi-ap`); проверка `promtool check config` — SUCCESS; перечитывание сигналом без перезапуска (`curl -X POST http://127.0.0.1:9090/-/reload`, HTTP 200).

## Что выполняет служба на точках (только чтение)

`/proc/uptime`, `/proc/loadavg`, `/proc/meminfo` (время работы, нагрузка, память); `/proc/sys/kernel/hostname`, `/etc/openwrt_release` (имя, прошивка); `date -u +%s` (часы точки); `ls /sys/class/net` (поиск радио); `iwinfo <радио> info` (SSID, канал, шум, мощность); `/sys/class/net/<радио>/statistics/*` (байты, ошибки, потери); `iw dev <радио> station dump` (число клиентов и их сигнал). Опрос раз в минуту, параллельно по 9 точкам; вход только по ключу (`BatchMode`), проверка отпечатка точки включена (`StrictHostKeyChecking=yes`), в `known_hosts` служба ничего не пишет. Первая версия кода — 116 строк. 2026-11-16 служба обновлена (проверка серверов времени точек); см. документ о расхождении часов на точках доступа.

## Метрики (первая версия)

261 метрика за цикл: доступность точки (`up`), время работы, нагрузка, свободная память; по каждому радио (18 радио): канал, шум, мощность, число клиентов, байты, ошибки, потери, сигнал клиентов (при их наличии); `wifi_ap_clock_offset_seconds` (расхождение часов точки и сервера). Один цикл опроса занимает около 0,7 с, одна точка 0,66 с в среднем (максимум 0,69 с), служба занимает около 21 МБ ОЗУ.

## Откат

- Служба [D, по подтверждению администратора]: скрипт `uninstall.sh` (временная папка `/tmp/wifi-ap-exporter/`, могла быть удалена) останавливает и удаляет службу и каталог `/opt/wifi-ap-exporter`; вручную: `systemctl disable --now wifi-ap-exporter` и удалить файл службы и каталог.
- Правило порта [W]: `sudo ufw delete allow from 192.168.12.202 to any port 9877 proto tcp`.
- Ключ на точке [W]: `sed -i '/monitoring-ap@wmswifi/d' /etc/dropbear/authorized_keys`; ключ на `wmsWiFi` удалить вручную, если он больше не нужен.
- Prometheus [W]: вернуть `prometheus.yml` из `prometheus.yml.bak-20261116`, удалить `targets/wifi.yml`, перечитать конфиг (`curl -X POST http://127.0.0.1:9090/-/reload`).

## Решения и риски

- Ключ без пароля на `wmsWiFi` даёт вход на все 9 точек (решение администратора). Можно ограничить ключ на точках только для чтения параметром `command=`, но набор команд пришлось бы фиксировать заранее: не делалось.
- Отдельный риск: до первого опроса после перезагрузки `wmsWiFi` точки могут показаться недоступными (сеть ещё не поднялась); через минуту должно прийти в норму (INFERRED).
- Контейнеры стека Qtech (nginx, backend, mongo, mqtt, strongswan) метрики `node-exporter` не показывают: для них нужен отдельный источник (например, cAdvisor), это отдельная задача и в этом документе не решалась.
