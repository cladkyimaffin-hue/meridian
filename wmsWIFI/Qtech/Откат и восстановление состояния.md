Прогресс: DNS через /etc/hosts сработал — IKE теперь доходит до сервера, и SA частично поднялась (видны реальные SPI). Но новая ошибка: дубликат существующей CHILD_SA — на сервере/точке уже висит недоубитая SA {3} с теми же TS (10.9.255.65/32 ↔ 10.9.0.1/32), и новая {4} конфликтует с ней.

Быстрый фикс — сбросить старые SA и попробовать снова:

bash
ipsec down wimark-wtm
ipsec statusall
Если после down всё равно висит старая SA (не убьётся) — форсируем полную перезагрузку демона на точке:

bash
/etc/init.d/ipsec restart
sleep 3
ipsec up wimark-wtm
Выполните ipsec down wimark-wtm, затем ipsec statusall — покажите результат.

Корневая причина на .164 подтверждена: отсутствовала запись WIFI-CONTROLLER.localdomain в /etc/hosts → DNS resolve failed → IKE даже не пытался уйти в сеть.
Фикс: echo "192.168.12.154 WIFI-CONTROLLER.localdomain" >> /etc/hosts, затем ipsec down/up для сброса дублирующейся SA.
Важный вывод: скорее всего это системная проблема — у остальных 6 офлайн-точек (ed08, ee34, ee64, ee91, ef60, f09e), вероятно, та же причина (нет записи в /etc/hosts или сбой локального DNS-резолвера на точке).

После перезагрузки тд настройки теряются

Это меняет картину — значит /etc/hosts на этих точках не персистентный (типично для OpenWrt-подобных прошивок: /etc/hosts генерируется заново при каждой загрузке из /etc/config/dhcp или overlay сбрасывается).

Протокол (обновлено):

Фикс через прямой echo >> /etc/hosts — временный, не переживает ребут.
Нужно найти постоянное место для этой записи, которое не затирается при загрузке.
Проверим, где реально генерируется /etc/hosts на этой платформе:

bash
ls -la /etc/hosts
uci show dhcp | grep -i host
cat /etc/config/dhcp | grep -A3 host
Это покажет, управляется ли /etc/hosts через UCI (/etc/config/dhcp, секции config domain или config host) — если да, добавление записи через uci переживёт перезагрузку.

Дайте вывод — тогда сделаем постоянный фикс на .164, а затем применим то же самое ко всем офлайн-точкам.
