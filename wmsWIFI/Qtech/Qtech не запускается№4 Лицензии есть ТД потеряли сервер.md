## 3. Главная находка и решение этой сессии
 
### Исходная проблема
9 устройств QTECH QWP-82 отображались в интерфейсе Wimark ONE как "офлайн", хотя физически пинговались.
 
### Ход расследования (кратко)
1. Первоначальная гипотеза про "устройства не знают адрес MQTT-брокера" (из-за отключённого DHCP Option 43) — оказалась неверной.
2. tcpdump на хосте показал: устройства сами инициируют IKEv2/IPsec (ikev2_init) на 192.168.12.154:500 — адрес сервера устройствам известен, транспорт для управляющего трафика (включая MQTT) — это IPsec-туннель.
3. IPsec реализован через strongSwan (charon), запущенный в отдельном Docker-контейнере one-strongswan-1 (образ wne/strongswan:alpine-5.9.10), в режиме network_mode: host. Конфиги — не в стандартных /etc/, а в /opt/wimark/etc/strongswan/ (strongswan.conf, ipsec.conf.tmpl, run.sh).
4. ipsec statusall показывал 0 активных SA — ни одно устройство не может установить туннель, хотя ранее (до какого-то момента) успешные подключения были.
5. КОРНЕВАЯ ПРИЧИНА: UFW (firewall на хосте) был настроен с политикой deny incoming по умолчанию и не содержал разрешающих правил для портов 500/udp и 4500/udp (IKE и IKE NAT-T). Подтверждено логами journalctl -k | grep "UFW BLOCK" — массовые блокировки пакетов от ВСЕХ Qtech-устройств на порт 500.
 
### Применённое решение
ufw allow 500/udp
ufw allow 4500/udp
 
Правила применились (IPv4 и IPv6). После этого 7-8 из 9 устройств (.158, .160, .161, .162, .164, .165, .166) в течение 1-2 минут успешно установили IKE_SA и CHILD_SA (подтверждено через docker exec -it one-strongswan-1 ipsec statusall), и UI Wimark начал показывать их как "онлайн".
 
### Побочные находки, закрытые как нерелевантные
- Порт 41113 на хосте слушает сторонний процесс mihomo (VPN-клиент пользователя, не относится к Wimark) — устройства пытались стучаться туда, но это не блокирует работу Wimark; пользователь останавливал его для проверки, можно запускать обратно.
- В config_rule (MongoDB) шаблон "QTECH QWP-82" не содержит параметров туннеля (tunnels: {}) — это нормально, конфигурация подключения идёт через IPsec на уровне ipsec.conf, а не через применяемый в UI шаблон устройства. Задача №2 из исходного протокола (почему шаблон не обновляет устройства), возможно, вообще неактуальна.
 
## 4. Открытый вопрос (не решён, точка возобновления)
 
Устройство Qtech-ee34 (192.168.12.163) остаётся офлайн — единственное из 9.
 
Диагностика показала:
- Устройство отвечает на ICMP (ping — RTT ~1мс, физически доступно и работает в сети).
- В ipsec statusall для него нет активной или устанавливаемой SA (при том что 7 других устройств имеют стабильные активные туннели).
- tcpdump по .163 показывает только mDNS-запросы (224.0.0.251:5353 — ищет Keenetic-F3.local, openbmc-scalable.local, wmsbackup.local), но ни одного пакета на UDP/500 (IKE) — то есть, в отличие от остальных 8 устройств, .163 вообще не пытается инициировать IPsec-соединение.
- Последняя команда, отправленная на проверку (результат ожидается в новой сессии):
  timeout 180 tcpdump -i eth0 host 192.168.12.163 -n
  (3-минутный захват трафика, чтобы окончательно исключить редкие попытки подключения перед тем, как переходить к диагностике самого устройства).
 
### Гипотеза для .163
Проблема специфична для этого конкретного устройства (не сетевая/firewall — то, что чинили в этой сессии, уже решено), вероятно:
- завис IPsec-клиент/демон на самой точке доступа;
- требуется физическая перезагрузка устройства (питание/PoE reset);
- либо иная локальная неисправность прошивки.
 
### Следующие шаги в новой сессии
1. Дождаться и проанализировать результат timeout 180 tcpdump -i eth0 host 192.168.12.163 -n — если за 3 минуты нет пакетов на порт 500/udp, гипотеза подтверждена.
2. Если подтверждено — обсудить с пользователем возможность перезагрузки .163 (PoE reset через коммутатор, если поддерживается, либо физическое отключение).
3. Параллельно можно закрыть или сузить правила UFW: сейчас 500/udp и 4500/udp открыты для Anywhere — по желанию можно ограничить источник до 192.168.12.0/24, если это приемлемо по безопасности (уточнить у пользователя).
4. Вернуться к задаче №2 из исходного протокола (почему применение шаблона QTECH QWP-82 через UI не обновляло конфигурацию) — вероятно, неактуальна в свете новой картины, но стоит перепроверить, если появятся дополнительные симптомы.
5. Задача №3 (сброс пароля root на LuCI устройств) — не рассматривалась в этой сессии, остаётся открытой, если понадобится доступ к самим точкам для диагностики зависшего IPsec-клиента на .163.
 
## 5. Рабочие команды-шпаргалка для новой сессии
 
# Статус IPsec-туннелей
docker exec -it one-strongswan-1 ipsec statusall
 
# Живые логи strongSwan
docker logs -f --tail 50 one-strongswan-1
 
# Проверка блокировок UFW в реальном времени
journalctl -k -f | grep -i "UFW BLOCK"
 
# Текущие правила UFW
ufw status verbose
 
# Проверка конкретного устройства
ping -c 4 <IP>
tcpdump -i eth0 host <IP> -n
